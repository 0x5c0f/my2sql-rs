## 输入

- `data/bench/mysql-bin.000003` = **554,555,214 B（528.8 MiB）** ≥ 500MB ✅
- 生成：`bash tools/gen-bench-binlog.sh`（一次性，缓存于 git-ignored `data/bench/`，
  marker `.bench-ready` + 尺寸校验；`FORCE=1` 重生成）。
- 方法学记录（简报偏差，如实入账）：简报称「gen-data.sql ×20 放大」，实测一次
  全量回放仅产 **~37KB** binlog（差分产物里 000002 的 ~3MB 实为镜像初始化期
  系统 schema DDL，非用户数据）。故放大改用 `tools/bench-growth.sql` 的
  `bench.t_grow` 富类型表（VARCHAR/TEXT/BLOB(含非UTF8)/DECIMAL(20,10)/DOUBLE/
  UNSIGNED/时间全族 fsp6/JSON/ENUM/SET/BIT(64)/YEAR + 边界/NULL/零值/emoji）
  + 存储过程 `grow_round()` 服务端放大：每轮 3×分批 INSERT…SELECT（各 1 万行）
  + 全镜像 UPDATE 3000 行 + DELETE 2000 行，共 62 轮（~2 分钟）过线；
  收尾 `FLUSH BINARY LOGS` 封口、root 助手容器 `chmod a+r`（uid999 教训同
  run-difftest）、debug 构建在线 `--uri` 全量冒烟 + `--schema-dump`。
- 事件构成：69,557 个被派发 rows 事件、1,757,221 条语句、errors=0
  （被测二进制运行摘要行，threads=1 与 8 完全一致）。

## 结果（criterion 0.8.2，sample_size=10）

| bench | time（点估计 min/median/max） | 吞吐 | DoD-3 (≥40MB/s) |
|---|---|---|---|
| **file_to_sql / threads=8** | 5.050 s / **5.093 s** / 5.141 s | **103.85 MiB/s ≈ 108.9 MB/s** | **PASS（2.7×）** |
| file_to_sql / threads=1（扩展性参考） | 12.715 s / 12.783 s / 12.856 s | 41.37 MiB/s ≈ 43.4 MB/s | （单线程已过 40MB/s 线） |

判定口径：`Throughput::Bytes(binlog 输入字节)`，即 **binlog MB/s**；
MiB/s×1.048576 = MB/s（10⁶ B）。原始日志：`out/bench-criterion.log`（git-ignored）。

criterion 输出摘录：

```text
file_to_sql/threads=8/528 MiB
                        time:   [5.0501 s 5.0927 s 5.1408 s]
                        thrpt:  [102.88 MiB/s 103.85 MiB/s 104.72 MiB/s]
file_to_sql/threads=1/528 MiB
                        time:   [12.715 s 12.783 s 12.856 s]
                        thrpt:  [41.137 MiB/s 41.371 MiB/s 41.593 MiB/s]
```

### 扩展性诚实注记

threads 1→8 仅 **2.5×**（非 8×）。瓶颈不在解码 CPU（单线程已 41MiB/s），
在流水线共享环节：dispatcher 单线程（schema 配对/Arc 下发）+ reorder 保序
缓冲 + 落盘写放大（528.8MiB binlog → 实测 871MB SQL 文本，约 1.65× 放大，
写盘与 page cache 回写
占大头）。DoD-3 达标不依赖该余量；并行效率优化（如分片写盘、批量下发）
记 P2/P3 候选，非收尾阻塞项。

## 复现

```bash
bash tools/gen-bench-binlog.sh     # ~5 分钟（docker，缓存命中即跳过）
cargo bench --bench decode         # ~3.5 分钟；输入缺失时 bench 跳过并 exit 0
                                   # （不破坏 cargo test --all-targets 洁净门禁）
```

（1 vs 4，字节相等断言）；528MiB 大盘上的 1-vs-8 对拍记录在
`out/bench-criterion.log`（gitignore，重跑 bench 即再生）。

## Release 构建（Task 16 Step 3）

| 目标 | 结果 |
|---|---|
| `cargo build --release`（glibc 动态） | ✅ `target/release/my2sql-rs`（4.08MB，ldd: libc/libz/libgcc） |
| `cargo build --target x86_64-unknown-linux-musl` | ✅ **意外全绿**——本机已装 musl std 目标 + `/usr/bin/x86_64-linux-musl-gcc`；产物 `static-pie linked, statically linked`（file 实证） |
| musl **release** 档 | ✅ `target/x86_64-unknown-linux-musl/release/my2sql-rs`（4.29MB，`--version` 可运行） |

### musl 静态二进制的性能悬崖（实测入账，勿踩）

同一 528.8 MiB bench binlog、同一 to-sql 负载：

| 二进制 | threads=1 | threads=8 |
|---|---|---|
| glibc release | 12.78 s | **5.09 s**（基线口径） |
| musl static release | 38.3 s（≈3× glibc） | **165 s ≈ 3.4 MiB/s**（比 1 线程还慢 4.3×） |

threads=8 反而暴跌 → 典型 **musl malloc 跨线程 arena 锁竞争**（分配密集流水线
+ 8 worker 共享全局堆）；单线程亦有 3× 差距（musl allocator/memcpy 常数）。
**P1 DoD-3 基线口径 = 原生 glibc release 构建（通过，见上表）**；musl 构建
仅保证「能编译、能跑对」，作为分发产物挂 P4 处理（候选缓解：mimalloc/jemalloc
挂钩、或 glibc-static 链接——届时验证，勿在 P1 引入新依赖）。
> P4 挂账「musl 静态构建」提前销账（构建维度），性能维度新挂账如上。
